O que você precisa fazer

Instale o plugin, abra o Claude Code na pasta do dent2dent e comece toda mudança pequena com /dent2dent:fase-dinamica. Ele planeja, abre a issue, implementa com teste, passa por um auditor e só publica depois que você responder "Mergeio?". O PR vai para a develop; a main continua com você.

01

Por que usar

Sem rito, o Claude implementa o que entendeu, no chat em que está, e o contexto some quando o chat compacta ou fecha. O plugin muda três coisas:

plano
Antes de codar
Nada nasce no GitHub sem você aprovar o plano. O plano vira a régua do auditor.
issue
Estado no GitHub
Cada etapa grava um comentário na issue. Chat novo ou compactado retoma de onde parou.
auditor
Olho de fora
Um agente de contexto limpo compara o que foi feito com o plano e aponta o que fugiu.
02

Instalar, uma vez

  1. Aceite o convite da org Dente2Dente no GitHub (o repositório do plugin é privado).
  2. No terminal, com gh, git e python3 instalados: 
    gh auth login
gh auth setup-git
  3. Dentro do Claude Code: 
    /plugin marketplace add Dente2Dente/dent2dent-skills
/plugin install dent2dent@dent2dent-skills
  4. Reinicie o Claude Code. Digite /dent2dent: e confira que aparecem as seis skills.

Quando o Hugo publicar melhoria no núcleo, você atualiza com /plugin marketplace update dent2dent-skills e reinicia.

03

Qual skill chamar

SkillQuandoO que sai
/dent2dent:fase-dinamicaAjuste, correção ou melhoria de até 5 passos, um assunto sóIssue com o plano, branch, commits com teste, PR e merge
/dent2dent:explorar"E se a gente...", dúvida entre caminhos, medir se algo funcionaA ata da discussão, que já chama a fase certa no mesmo chat
/dent2dent:fase1-planejarMódulo novo, várias telas, mais de um assuntoPlano, árvore Epic, Feature, PBI e Task em issues, spec no site de docs
/dent2dent:fase2-executarDepois da fase1, num chat novo pelo botão que ela ofereceUma Task por agente, auditor por PBI, PR por Feature, um "Mergeio?" no fim
/dent2dent:fase3-polirDepois da fase2, com você olhando a tela no localhostAjustes em lotes, regra nova gravada no repo, Epic fechado
/dent2dent:guia-usuarioDepois do polimento, quando alguém de fora vai usar a telaPDF com print de cada tela, bolinhas numeradas e legenda

Na dúvida, fase-dinamica. Se o plano passar de 5 passos, ela mesma recomenda a fase1 e pergunta se segue.

04

Como a fase-dinamica anda

plano no chat→ issue no GitHub→ branch e worktree→ teste, código, commit→ auditor→ polir (opcional)→ PR e "Mergeio?"

Você só responde em três pontos. O resto anda sozinho e é anunciado em uma linha.

PerguntaO que decidir
"Fecho o plano?"Se os passos, os arquivos e o critério de pronto estão certos. Corrija aqui: é barato. Depois disso o plano vira o corpo da issue.
"Polir antes do PR?"O auditor sugere melhorias. Sim, para fazer agora; não, para ir direto ao PR.
"Mergeio?"O merge publica. Confira o PR e responda sim só quando quiser no ar.

Frases que funcionam

/dent2dent:fase-dinamica O filtro de recebimentos não respeita a data final.

/dent2dent:explorar Quero repensar como a esteira de recebimentos avisa o atraso.

/dent2dent:fase1-planejar Módulo de agenda de entregas para os laboratórios.
05

No repositório da Dent2Dent

Hoje o seu fluxo é feat/* para a develop (homologação, Vercel e migrations do Supabase de HML) e depois a develop para a main (produção; as migrations de PROD rodam à mão, pelo workflow que pede "aplicar").

O plugin lê o tronco do repo

As skills perguntam ao GitHub qual é a branch padrão do repo, que aqui é a develop. A branch nasce dela e o PR volta para ela, então o merge cai em homologação. Se um dia a branch padrão mudar, o plugin acompanha sem você avisar.

Migrations

O seu AGENTS.md já diz que migration aplicada é imutável e que toda mudança de banco é migration nova. As skills leem esse arquivo antes de planejar e param antes de qualquer migration contra produção.

Testes

O teste do passo roda com npm test (vitest), primeiro falhando e depois passando. Banco de teste é sempre o local, nunca o do .env.

Promover para produção continua com você: quando a develop estiver homologada, abra o PR de develop para main como já faz, ou peça ao Claude para abrir e conferir antes do seu ok.

07

Erros comuns

  • Pedir para "só fazer rapidinho". O plano de um ajuste cabe em 5 linhas e é ele que o auditor usa. Sem plano, a auditoria vira opinião.
  • Responder "sim" no "Mergeio?" sem abrir o PR. O merge publica.
  • Abrir chat novo e recolar contexto. Não precisa: chame a mesma skill no chat novo e ela acha a issue pelo nome da branch.
  • Mergear a develop na main antes de homologar. A promoção continua com você (seção 05).
  • Pôr dado real no site de docs. Ele é público e não tem login.
08

Quando travar

Skill que errou de comportamento ou pediu algo estranho: mande para o Hugo o print e o link da issue. A correção entra no núcleo, desce para o seu marketplace no próximo sync e você atualiza com /plugin marketplace update dent2dent-skills.
